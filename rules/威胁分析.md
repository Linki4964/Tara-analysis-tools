# 威胁分析

## 概述

威胁分析（Threat Analysis）是 TARA 分析的第三步，在资产识别和损害场景定义完成后，基于 STRIDE 模型识别出针对已识别资产的潜在威胁场景。每个威胁是对"损害场景如何被实现"的进一步细化。

本规范基于 ISO/SAE 21434 标准，定义威胁场景的编号规则、STRIDE 分类标准和威胁描述编写规范。

---

## 一、威胁场景 ID

威胁场景 ID 命名规则：

```
CsTS_AS_<资产类型缩写>_<三位序号>
```

**格式说明：**

| 组成部分 | 含义 | 规则 |
|---------|------|------|
| `CsTS` | Cyber Security Threat Scenario | 威胁场景前缀 |
| `AS_<类型缩写>` | 引用资产 ID 的类型前缀 | 与关联资产的类型保持一致：`Da`/`Hw`/`Sw`/`Ee`/`Dt` |
| `_<三位序号>` | 从 001 开始递增 | 按 STRIDE 顺序排列，同一资产下有多个威胁时独立编号 |

**示例：**
- `CsTS_AS_Da_001` — 资产 AS_Da_001 的第一个威胁场景
- `CsTS_AS_Da_002` — 资产 AS_Da_001 的第二个威胁场景
- `CsTS_AS_Hw_001` — 资产 AS_Hw_001 的第一个威胁场景

**关联关系：**
- 每个威胁场景对应一个损害场景（CsDS），通过资产 ID + 安全属性建立关联
- 同一损害场景可能对应多个威胁场景（多种攻击手段达成同一损害）

---

## 二、威胁类型 — STRIDE 模型

威胁分析采用 STRIDE 威胁模型，六大类别如下：

| 类别 | 英文 | 缩写 | 定义 | 对抗的安全属性 |
|------|------|------|------|---------------|
| 欺骗 | Spoofing | S | 冒充合法身份或实体，获取系统信任 | 真实性 Authenticity |
| 篡改 | Tampering | T | 未授权修改数据、代码或配置 | 完整性 Integrity |
| 否认 | Repudiation | R | 执行操作后否认行为，缺少可追溯证据 | 不可否认性 Non-repudiation |
| 信息泄露 | Information Disclosure | I | 未授权获取/访问受保护的信息 | 保密性 Confidentiality |
| 拒绝服务 | Denial of Service | D | 使系统资源不可用，阻断正常服务 | 可用性 Availability |
| 权限提升 | Elevation of Privilege | E | 未授权获取更高权限，执行越权操作 | 授权 Authorization |

### STRIDE 与安全属性对应关系

```
STRIDE 类别              受影响的安全属性
─────────────────────────────────────────
Spoofing (S)     →    Authenticity (真实性)
Tampering (T)    →    Integrity (完整性)
Repudiation (R)  →    Non-repudiation (不可否认性)
Info Disclosure (I) → Confidentiality (保密性)
Denial of Service (D) → Availability (可用性)
Elevation of Privilege (E) → Authorization (授权)
```

### STRIDE 在汽车场景中的典型攻击示例

| STRIDE | 汽车典型场景 |
|--------|------------|
| **S - 欺骗** | 伪造 APP/TSP 身份发送远程控车指令；仿冒诊断设备身份接入 GW 网关；克隆合法钥匙信号欺骗 PEPS |
| **T - 篡改** | 篡改 CAN 总线报文修改指令内容；篡改固件包植入恶意代码；修改故障日志隐藏攻击痕迹 |
| **R - 否认** | 诊断设备执行非法操作后无日志可追溯；远程指令下发后发送方否认操作行为 |
| **I - 信息泄露** | 窃听 CAN 总线获取敏感数据；读取 MCU 安全密钥；导出车主隐私数据（位置、行驶轨迹） |
| **D - 拒绝服务** | CAN 总线泛洪攻击阻断正常通信；远程指令链路被干扰导致功能失效；诊断接口被持续占用 |
| **E - 权限提升** | 通过 OBD 接口获取网关管理权限；利用 SOC 系统漏洞获取 root 权限访问全车资源 |

### STRIDE 与损害场景安全属性的匹配规则

威胁分析时，STRIDE 类别的选择应**与损害场景的安全属性保持一致**：

| 损害场景的安全属性 | 优先考虑的 STRIDE 类别 |
|-------------------|----------------------|
| 保密性 Confidentiality | **I - 信息泄露**（主要），E - 权限提升（导致越权读取） |
| 完整性 Integrity | **T - 篡改**（主要），S - 欺骗（伪造数据来源） |
| 可用性 Availability | **D - 拒绝服务**（主要），T - 篡改（破坏数据导致服务异常） |

> 注意：一个损害场景可能通过多种 STRIDE 方式实现。例如"远程指令被篡改"可能涉及 S（身份欺骗后下发假指令）或 T（中间人篡改传输内容）。应分别编写独立的威胁场景。

## 三、威胁场景描述编写规范

### 编写公式

威胁场景描述遵循以下公式：

> **[攻击者/角色] + [利用 STRIDE 手段] + [针对目标资产] + [如何实现攻击效果] + [导致的损害场景]**

### 编写要点

1. **从攻击者视角编写**：描述"攻击者如何做"而非"系统被怎样"
2. **明确攻击手段**：清楚说明使用了什么 STRIDE 类型的攻击手段
3. **引用损害场景**：结尾关联到具体的损害场景 ID，保持追溯链
4. **描述具体可行**：攻击描述应具有技术可行性，而非抽象概念
5. **一个威胁一个手段**：每个威胁场景只描述一种 STRIDE 类型的攻击

### 标准示例

#### 欺骗 Spoofing 示例

```
[[Spoofing]] 攻击者伪造合法 APP 身份凭证，通过 TSP 平台鉴权漏洞冒充授权用户，
向 TBOX 下发伪造的远程解锁指令，绕过正常身份认证机制，非法进入车辆。
→ 关联损害场景: CsDS_AS_Da_019（远程闭锁/解锁信号完整性被破坏，车门异常解锁）
```

#### 篡改 Tampering 示例

```
[[Tampering]] 攻击者通过物理接入 OBD 接口，利用 CAN 总线未加密传输的特点，
拦截并篡改 VCU 向 MCU 下发的扭矩控制报文，注入恶意扭矩参数，导致车辆非预期加减速。
→ 关联损害场景: CsDS_AS_Da_077（驱动扭矩指令完整性被破坏）
```

#### 信息泄露 Information Disclosure 示例

```
[[Information Disclosure]] 攻击者在车辆附近部署 CAN 总线嗅探设备，通过逆向 CAN 通信矩阵，
持续监听并解析 TBOX 与 VCU 之间的远程控制交互报文，获取远程启动/关闭指令的发送规律与控制逻辑。
→ 关联损害场景: CsDS_AS_Da_001（远程启动/关闭信号机密性被破坏）
```

#### 拒绝服务 Denial of Service 示例

```
[[Denial of Service]] 攻击者通过无线信道持续向 TBOX 发送大量畸形远程指令报文，
耗尽 TBOX 通信处理资源，导致合法远程控车指令（启动/闭锁/空调）无法正常接收与转发。
→ 关联损害场景: CsDS_AS_Da_005（远程启动/关闭信号可用性被破坏）
```

#### 权限提升 Elevation of Privilege 示例

```
[[Elevation of Privilege]] 攻击者通过外部诊断设备接入 OBD 接口，利用诊断会话权限校验缺陷，
绕过 GW 网关的访问控制策略，获取整车控制器（VCU）的诊断改写权限，篡改限速保护参数。
→ 关联损害场景: CsDS_AS_Da_014（远程限速指令完整性被破坏）
```

## 四、威胁场景与上下游关联关系

### 追溯链

TARA 分析的每个步骤之间通过 ID 建立完整追溯链：

```
资产(AS) → 损害场景(CsDS) → 威胁场景(CsTS) → 攻击路径(AP) → 风险处置(RT)
   │            │               │              │             │
   └── 1:1 ────┘│               │              │             │
                └──── 1:N ──────┘│              │             │
                                 └───── 1:N ───┘│             │
                                                └──── 1:1 ──┘│
                                                              └── + 安全声明(Claim)
```

- 一个资产 → 多个损害场景（按安全属性拆分）
- 一个损害场景 → 多个威胁场景（多种 STRIDE 手段）
- 一个威胁场景 → 一个或多个攻击路径（不同攻击入口/路径）
- 一个攻击路径 → 一个风险处置决策 + 安全声明

### 关联字段映射

在威胁场景记录中，需明确填写以下关联字段：

| 字段 | 说明 | 示例 |
|------|------|------|
| 资产 Asset | 关联的资产 ID + 名称 | `AS_Da_001 远程启动/关闭信号` |
| 威胁类型 | STRIDE 分类 | `信息泄露 Information Disclosure` |
| 威胁场景 ID | CsTS 编号 | `CsTS_AS_Da_001` |
| 威胁描述 | 攻击者视角描述 | 见上节示例 |
| 关联损害场景 | 指向对应的 CsDS | `CsDS_AS_Da_001` |

## 五、威胁严重程度评估

威胁严重程度（Threat Severity）继承自对应损害场景的影响等级（Impact Level），用于后续攻击路径分析中的影响等级 IL 判定。

| 损害场景影响等级 | 威胁严重程度 | 说明 |
|----------------|------------|------|
| Minor（轻微） | Low | 威胁即使实现，造成的影响也很小 |
| Moderate（中等） | Medium | 威胁实现会造成一定范围的影响 |
| Major（主要） | High | 威胁实现会造成较大影响 |
| Severe（严重） | Critical | 威胁实现会造成严重影响 |

> 注意：威胁严重程度并不直接等于最终的风险等级。风险等级需在攻击路径分析中综合考虑攻击可行性后判定。

## 六、填写完成检查清单

- [ ] 威胁场景 ID 符合 `CsTS_AS_<类型>_<序号>` 格式
- [ ] 每个损害场景至少识别了 1 个威胁场景
- [ ] STRIDE 类别选择与损害场景的安全属性匹配
- [ ] 威胁描述从攻击者视角编写，技术手段明确
- [ ] 威胁描述结尾关联了具体的损害场景 ID
- [ ] 每个威胁场景只描述一种 STRIDE 类型
- [ ] 威胁严重程度等级与损害场景影响等级保持一致
- [ ] 资产 ID 正确关联到对应的 CsDS
