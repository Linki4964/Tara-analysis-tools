# 网络安全相关项描述

## 概述

网络安全相关项定义是 TARA 分析的第一步，用于识别系统中所有值得保护的资产（Asset），并按照统一规范进行分类、编号和功能描述。资产的分类准确性直接影响后续损害场景编写、威胁分析和风险评级的质量。

本规范基于 ISO/SAE 21434 标准，结合汽车电子电气架构特点，定义 5 大资产类别及其填写标准。

---

## 一、分类定义与判定规则

请严格依据以下 5 个资产类别及其判定规则进行分类：

### 1. 数据流（Data Flow）

| 属性 | 说明 |
|------|------|
| **定义** | 在系统/组件之间**动态传输**的信息、指令、信号、报文或状态反馈。数据流描述的是"传输中的信息"，而非信息本身。 |
| **核心判据** | 存在传输方向（发送方→接收方），具有动态、实时、端到端的特征 |
| **编号前缀** | `AS_Da_` |

**特征词/模式：**
- 信号类：`xxx信号`、`xxx状态信号`、`xxx反馈信号`
- 指令类：`xxx指令`、`xxx请求`、`xxx控制信号`
- 交互类：`xxx交互信号`、`xxx应答`
- 名称中包含传输方向箭头：`A→B`（单向）、`A↔B`（双向）
- 名称中带有括号标注的通信路径：`信号名（发送方→接收方1→接收方2）`

**典型示例：**
| 资产编号 | 资产名称 | 说明 |
|---------|---------|------|
| AS_Da_001 | 远程启动 / 关闭信号（APP/TSP→TBOX→VCU） | 跨多节点下行指令流 |
| AS_Da_005 | 门锁状态信号（BCM→TBOX→APP/TSP） | 状态上行反馈流 |
| AS_Da_081 | 充电交互信号（VCU↔BMS/OBC） | 双向握手交互流 |
| AS_Da_095 | 电池温度信号（BMS→VCU） | 传感器数据单向流 |

**容易混淆的边界案例：**
- ❌ "整车 CAN 总线" → 这是物理通信介质，属于**硬件**
- ❌ "CAN 通信协议栈" → 这是通信规则/程序，属于**软件**
- ✅ "车速信号（VCU/ESP→BCM）" → 在 CAN 总线上传输的具体数据，属于**数据流**
- ❌ "MCU 故障日志" → 这是静态存储的记录，属于**数据**
- ✅ "DTC 故障码信息（VCU→仪表/诊断设备）" → 这是传输中的故障信息，属于**数据流**

---

### 2. 硬件（Hardware）

| 属性 | 说明 |
|------|------|
| **定义** | 承载业务运行、数据存储、通信转发的**物理实体**，包括电子控制单元（ECU）、芯片、传感器、执行器、物理通信总线等。 |
| **核心判据** | 可触摸的物理设备，具有独立的硬件编号/料号，是软件运行的载体 |
| **编号前缀** | `AS_Hw_` |

**特征词/模式：**
- 控制器/ECU：`VCU`、`BCM`、`MCU`、`BMS`、`GW`、`TBOX`、`OBC`
- 芯片级：`SOC`、`MCU 主控芯片`
- 物理总线/网络：`整车 CAN 总线`、`LIN 总线`、`以太网`
- 传感器/执行器：`加速踏板传感器`、`制动踏板传感器`、`高压继电器`

**典型示例：**
| 资产编号 | 资产名称 | 说明 |
|---------|---------|------|
| AS_Hw_001 | SOC | 座舱主控芯片 |
| AS_Hw_002 | MCU | 电机控制器 |
| AS_Hw_003 | BCM | 车身控制器 |
| AS_Hw_004 | VCU | 整车控制器 |
| AS_Hw_010 | 整车 CAN 总线 | 车内主干通信网络 |

**容易混淆的边界案例：**
- ❌ "SOC 固件包" → 这是烧录到 SOC 的软件程序，属于**软件**
- ❌ "TSP 平台" → 这是云端系统，不属于车载物理硬件，属于**外部实体**
- ✅ "TBOX" → 车载物理通信终端，属于**硬件**
- ✅ "GW 网关" → 车载物理网关控制器，属于**硬件**

---

### 3. 软件（Software）

| 属性 | 说明 |
|------|------|
| **定义** | 运行于硬件之上的**代码程序、固件包、操作系统、算法库或通信协议栈**，具备刷写、升级、配置或执行逻辑的能力。 |
| **核心判据** | 非物理实体，可被刷写/升级/配置，以二进制/代码形式存在 |
| **编号前缀** | `AS_Sw_` |

**特征词/模式：**
- 固件类：`xxx固件包`、`xxx固件`、`xxx程序`
- 操作系统类：`Android 操作系统`、`RTOS`、`Linux`
- 协议栈/中间件：`CAN 通信协议栈`、`TCP/IP 协议栈`、` SOME/IP`
- 算法/策略：`xxx控制算法`、`xxx安全策略`

**典型示例：**
| 资产编号 | 资产名称 | 说明 |
|---------|---------|------|
| AS_Sw_001 | SOC 固件包 | SOC 底层运行程序与功能配置 |
| AS_Sw_002 | Android 操作系统 | 车载 IVI 应用运行环境 |
| AS_Sw_003 | MCU 固件包 | 电机控制算法与安全保护策略 |
| AS_Sw_009 | CAN 通信协议栈 | 整车 CAN 报文封装/解析/校验基础服务 |

**容易混淆的边界案例：**
- ❌ "SOC" → 这是运行固件的芯片硬件，属于**硬件**
- ✅ "SOC 固件包" → 这是烧录到 SOC 的程序代码，属于**软件**
- ❌ "身份认证信息" → 这是软件使用的配置数据，属于**数据**
- ✅ "Android 操作系统" → 这是系统级软件，属于**软件**

---

### 4. 外部实体（External Entity）

| 属性 | 说明 |
|------|------|
| **定义** | 位于当前被评估系统/控制器**边界外部**，但与系统存在数据交互的实体、用户终端、云端平台或外部设备。 |
| **核心判据** | 不在被评估系统的物理/逻辑边界内，通过外部接口（公网、OBD 口、射频）与系统交互 |
| **编号前缀** | `AS_Ee_` |

**特征词/模式：**
- 用户终端：`手机`、`平板`
- 移动应用：`APP / 小程序`
- 云端平台：`TSP 平台`、`云端服务器`、`OTA 平台`
- 外部诊断设备：`外部诊断设备`、`OBD 检测设备`
- 边界外 ECU（系统交互方）：`SRS 安全气囊 ECU`、`PEPS 无钥匙系统`、`组合仪表`
- 充电设施：`充电桩`、`快充桩`

**典型示例：**
| 资产编号 | 资产名称 | 说明 |
|---------|---------|------|
| AS_Ee_001 | 手机 | 用户操作终端 |
| AS_Ee_002 | APP / 小程序 | 用户远程控车应用 |
| AS_Ee_003 | TSP 平台 | 云端业务管理平台 |
| AS_Ee_004 | 外部诊断设备 | 维修检测外设 |
| AS_Ee_006 | SRS 安全气囊 ECU | 碰撞安全联动 ECU（VIU 系统边界外） |

**边界判断规则：**
- 判断某 ECU 是"硬件"还是"外部实体"，取决于**被评估系统的边界定义**：
  - 如果被评估系统是 VIU（整车智能单元），则 VIU 包含的 SOC、MCU、BCM、VCU、GW、TBOX 等为**硬件**
  - 如果某 ECU（如 SRS、PEPS、组合仪表）不属于 VIU，但通过 CAN 总线与 VIU 交互 → 归类为**外部实体**
  - 如果后续分析范围扩大，某"外部实体"可能需要重新归类为"硬件"

---

### 5. 数据（Data Asset）

| 属性 | 说明 |
|------|------|
| **定义** | 在系统中**静态存储、配置或使用**的敏感信息、密钥、凭证、唯一标识、持久化记录或配置文件。 |
| **核心判据** | 存储中的信息（at rest），具有机密性/完整性保护需求，不以传输为存在形式 |
| **编号前缀** | `AS_Dt_` |

**特征词/模式：**
- 密钥/凭证类：`xxx密钥`、`根证书`、`身份认证信息`、`xxx凭证`
- 标识类：`车辆唯一标识 VIN`、`ECU 序列号`
- 日志/记录类：`xxx故障日志`、`xxx运行日志`、`xxx事件记录`
- 配置类：`xxx配置文件`、`xxx标定参数`

**典型示例：**
| 资产编号 | 资产名称 | 说明 |
|---------|---------|------|
| AS_Dt_001 | MCU 安全启动密钥 | 电机控制器底层可信安全凭证 |
| AS_Dt_002 | SOC 安全启动密钥 | IVI 底层可信根密钥 |
| AS_Dt_003 | 身份认证信息 | 用户凭证、车云会话密钥、设备校验信息 |
| AS_Dt_004 | 车辆唯一标识 VIN | 整车唯一身份编码 |

**容易混淆的边界案例：**
- ❌ "门锁状态信号（BCM→TBOX→APP/TSP）" → 这是正在传输的状态信息，属于**数据流**
- ✅ "MCU 故障日志" → 这是已存储的事件记录，属于**数据**
- ❌ "身份认证信息的传输指令" → 传输过程中的认证信息，属于**数据流**
- ✅ "身份认证信息" → 存储在设备中的凭证数据，属于**数据**

## 二、分类决策树

当面对一个资产难以判断类别时，按以下顺序依次判断：

```
资产识别入口
│
├─ 是否在系统边界外？ ──────────────── YES ──→ 外部实体（External Entity）
│   └─ NO
│
├─ 是否为物理设备/芯片/总线？ ────── YES ──→ 硬件（Hardware）
│   └─ NO
│
├─ 是否为代码/程序/固件/OS？ ─────── YES ──→ 软件（Software）
│   └─ NO
│
├─ 是否为动态传输中的信息/信号？ ─── YES ──→ 数据流（Data Flow）
│   └─ NO
│
└─ 是否为静态存储的信息/密钥/日志？ ─ YES ──→ 数据（Data Asset）
    └─ NO → 重新审视资产定义
```

## 三、五大类别对比速查表

| 维度 | 数据流 | 硬件 | 软件 | 外部实体 | 数据 |
|------|--------|------|------|---------|------|
| **存在形式** | 传输中的信号/指令 | 物理设备/芯片 | 代码/程序/固件 | 交互终端/平台 | 存储中的信息 |
| **动态/静态** | 动态（in transit） | 静态实体 | 可刷写/升级 | 独立运行 | 静态（at rest） |
| **编号前缀** | `AS_Da_` | `AS_Hw_` | `AS_Sw_` | `AS_Ee_` | `AS_Dt_` |
| **典型数量(VIU)** | 90+ | 10 | 9 | 8 | 6 |
| **安全属性侧重** | 保密性/完整性为主 | 可用性/完整性为主 | 完整性为主 | 保密性/完整性 | 保密性/完整性为主 |
| **常见威胁** | 窃听、篡改、伪造、重放 | 物理破坏、侧信道 | 逆向、篡改、植入 | 仿冒、越权、社工 | 泄露、篡改、删除 |

## 四、资产名称填写规范

### 1. 数据流类资产

**格式：** `[业务动作/用途] + [信号类型] + （发送方 → 中转节点 → 最终接收方）`

**规则：**
- 信号名称应体现业务含义，而非技术报文名
- 括号内用 `→` 标注完整传输路径，从数据源到最终目标
- 双向通信用 `↔` 表示
- 多个发送方或接收方用 `/` 分隔

**示例：**
```
远程启动 / 关闭信号（APP/TSP→TBOX→VCU）
高压 / 空调 / 加热唤醒 / 关闭信号（VCU→HVAC/EAS）
门锁状态信号（BCM→TBOX→APP/TSP）
充电交互信号（VCU↔BMS/OBC）
空调状态反馈信号（VCU→TBOX→TSP→APP）
```

### 2. 硬件类资产

**格式：** `[控制器/芯片/总线标准名称或通用缩写]`

**规则：**
- 使用行业通用缩写或标准名称
- 保持命名简洁，不加功能修饰语
- 如存在多实例，加编号区分（如 MCU_1、MCU_2）

**示例：**
```
SOC
MCU
BCM
VCU
GW 网关
TBOX
整车 CAN 总线
```

### 3. 软件类资产

**格式：** `[硬件/平台名称] + [软件类型：固件包/操作系统/协议栈]`

**规则：**
- 指明该软件运行的目标硬件
- 软件类型明确：固件包、操作系统、协议栈、算法库

**示例：**
```
SOC 固件包
Android 操作系统
MCU 固件包
CAN 通信协议栈
BCM 固件包
TBOX 固件包
```

### 4. 外部实体类资产

**格式：** `[实体通用名称]`

**规则：**
- 使用行业通用名称
- 如实体角色明确，可加角色前缀（如"外部诊断设备"）

**示例：**
```
手机
APP / 小程序
TSP 平台
外部诊断设备
OBD 检测设备
SRS 安全气囊 ECU
PEPS 无钥匙系统
组合仪表
```

### 5. 数据类资产

**格式：** `[数据所属系统/组件] + [数据内容/类型]`

**规则：**
- 明确数据的使用场景和内容
- 密钥类标注用途（如"安全启动密钥"）

**示例：**
```
MCU 安全启动密钥
SOC 安全启动密钥
身份认证信息
车辆唯一标识 VIN
MCU 故障日志
SOC 故障日志
```

## 五、资产编号规范

资产编号采用三段式结构：`AS_<类别缩写>_<三位序号>`

| 类别 | 缩写 | 格式 | 示例 |
|------|------|------|------|
| 数据流 | Da | `AS_Da_\d{3,}` | AS_Da_001 |
| 硬件 | Hw | `AS_Hw_\d{3,}` | AS_Hw_001 |
| 软件 | Sw | `AS_Sw_\d{3,}` | AS_Sw_001 |
| 外部实体 | Ee | `AS_Ee_\d{3,}` | AS_Ee_001 |
| 数据 | Dt | `AS_Dt_\d{3,}` | AS_Dt_001 |

**编号规则：**
- 每类资产独立编号，从 001 开始递增
- 序号不跨类跳跃（即 Da_001~Da_099, Hw_001~Hw_010 各自独立）
- 同类资产的编号建议按其功能相关性分组，如数据流按所属子系统排列

## 八、功能描述编写规范

资产的功能描述必须结合汽车网络安全评估规范（ISO/SAE 21434），遵循以下对应类别的句式结构与写作要求：

### 1. 数据流（Data Flow）功能描述

**句式结构：**
> `[动词]` + `[发起方/输入数据描述]` + `，经` + `[中转/路由节点]` + `，完成/执行` + `[业务校验与控制逻辑]` + `，将` + `[执行结果/反馈信号]` + `[传输至/反馈至]` + `[接收方/目的地]` + `。`

**动词选择指南：**
| 数据流方向 | 推荐动词 |
|-----------|---------|
| 下行（平台→车端） | 接收、解析 |
| 上行（车端→平台） | 采集、上传、反馈 |
| 横向（ECU 间） | 采集、驱动、下发、交互 |
| 反馈闭环 | 输出、同步 |

**编写要点：**
1. 动词开头，描述数据从哪来、经过谁、到哪去、做什么
2. 明确每个中转节点的处理动作（转发、校验、路由、解析）
3. 说明业务的闭环逻辑（请求→执行→反馈）

**标准示例：**
```
接收 APP/TSP 远程启动/关闭指令，经 TBOX 转发至 VCU，完成车辆状态与权限校验，
控制高压系统、空调及加热设备启停，将执行状态反馈至 TSP 平台与 APP。
```
```
采集 BCM 执行的灯光闪烁、喇叭鸣响状态，通过 TBOX、TSP 反馈至 APP。
```
```
接收 APP 空调远程启动/关闭指令，经 TSP、TBOX 转发至 VCU，校验电源、故障等级、
SOC 等条件，执行空调启停控制，将运行状态反馈至 APP。
```

**反面示例（不符合规范）：**
- ❌ "用于远程启动/关闭的信号" → 缺少动作描述和完整路径
- ❌ "远程控制的指令数据" → 缺少起点、终点和处理逻辑

---

### 2. 硬件（Hardware）功能描述

**句式结构：**
> `[资产名称]：` + `[接入/对接哪些总线与ECU]` + `，负责` + `[核心业务功能列表]` + `，存储` + `[运行数据/故障日志/配置]` + `，校验` + `[固件/数据完整性]` + `，执行` + `[安全防护/故障限制控制逻辑]` + `。`

**编写要点：**
1. 以"资产名称："开头
2. 先描述输入/接入（接了什么），再描述输出/执行（做什么）
3. 必须包含安全防护职责（校验、存储、防护、限制）
4. 说明在整车架构中的角色定位

**标准示例：**
```
SOC：接入整车 CAN 总线交互各 ECU 状态数据，接收 TBOX 同步的云端车辆信息，
承载VIU业务运行与人机数据展示，本地存储系统配置、运行日志及临时交互数据，
校验本地程序完整性，依托系统安全策略防止数据非法访问与篡改。
```
```
VCU：接收 TBOX 远程控制指令、各 ECU 工况及故障信号，统筹整车高压上下电、
能量管理、热管理、限速保护逻辑，与 BMS、MCU、OBC、GW 双向数据交互，
下发整车级控制指令，上传整车运行状态与故障信息至整车 CAN。
```
```
GW 网关：接收外部诊断设备、OBD 设备访问报文，完成车内多网段 CAN 报文路由
转发、协议转换，执行诊断访问权限过滤、非法报文拦截，隔离跨网段非法访问，
转发各 ECU 诊断请求与响应数据，保障车内网络边界安全。
```
